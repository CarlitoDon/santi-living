# Proxy Deployment — Coolify

Deployment target for `apps/proxy` (`@santi-living/proxy`) is a self-hosted
Coolify instance. The previous Hostinger SSH/rsync workflow
(`.github/workflows/deploy-proxy-hostinger.yml`) is removed; pushes no longer
deploy anywhere automatically.

## Branch mapping

`dev` branch → staging; `main` branch → production.

| Branch | Coolify resource | Secret used |
| ------ | ---------------- | ----------- |
| `dev`  | staging          | `COOLIFY_DEPLOY_WEBHOOK_PROXY_STAGING` |
| `main` | production       | `COOLIFY_DEPLOY_WEBHOOK_PROXY_PRODUCTION` |

## Required GitHub secrets

Configure both in **GitHub → Settings → Secrets and variables → Actions**:

- `COOLIFY_DEPLOY_WEBHOOK_PROXY_STAGING` — full webhook URL of the Coolify
  staging application (Coolify → app → Webhooks → "Deploy Webhook (API)").
- `COOLIFY_DEPLOY_WEBHOOK_PROXY_PRODUCTION` — same, for the production app.

Values are the deploy webhook URLs Coolify generates per application. They are
secret because they allow triggering a deployment; never paste them into logs,
PRs, or code. The workflow passes them to `curl` via job environment variables
and prints only the HTTP status code, never the URL or response body.

## GitHub workflow

`.github/workflows/deploy-proxy-coolify.yml`:

1. Builds `apps/proxy` on `ubuntu-latest` (quality gate, no deployment).
2. `deploy` job runs only on an explicit `workflow_dispatch` with an
   `environment` choice (`staging` | `production`), or as a reusable
   `workflow_call` from another trusted workflow.
3. POSTs to the matching webhook with:

   ```bash
   curl --fail --show-error --silent --max-time 30 \
     --output /dev/null --write-out '%{http_code}' \
     -X POST --header 'Content-Length: 0' "$WEBHOOK_URL"
   ```

   - `--fail` → 4xx/5xx responses fail the request.
   - The workflow also checks the returned status against `^2[0-9]{2}$`, so
     redirects (3xx) are not treated as success.
   - `--max-time 30` → bounded timeout; a hung Coolify endpoint fails fast.
   - Response body and curl diagnostics are discarded so neither response data
     nor a URL containing a webhook secret is echoed.

### Tunnel requirement (GitHub-hosted runners)

GitHub-hosted runners run on the public internet and **cannot reach a local
Coolify instance** (e.g. `http://localhost:8000` on your own machine or LAN).
Before triggering the workflow from GitHub, expose the Coolify webhook through
a public tunnel, for example:

```bash
cloudflared tunnel --url http://localhost:8000
# or: ngrok http 8000
```

Then set the secret to the exact public URL produced by the tunnel, preserving
the complete webhook path generated by Coolify. Do not invent or rewrite the
path. If no tunnel is available, do not trigger the workflow — instead trigger
the deploy webhook directly from a machine that can reach Coolify (see
"Manual trigger from LAN" below). This keeps deployments explicit instead of
failing silently.

The workflow also enforces the branch mapping at execution time: staging must
be dispatched/called from `dev`, and production must be dispatched/called from
`main`. A mismatched branch fails before any webhook request.

## Coolify application configuration (Dockerfile)

Configure both Coolify applications to build from the repository-root Docker
context using `apps/proxy/Dockerfile`. Do not use Nixpacks for this service:
the Dockerfile packages the workspace output and its runtime command together.

| Setting | Staging | Production |
| ------- | ------- | ---------- |
| Repository | `CarlitoDon/santi-living` | `CarlitoDon/santi-living` |
| Branch | `dev` | `main` |
| Build method | Dockerfile | Dockerfile |
| Dockerfile path | `apps/proxy/Dockerfile` | `apps/proxy/Dockerfile` |
| Build context / Root directory | `/` (repository root) | `/` (repository root) |
| Container port | `3002` | `3002` |
| Health check port | `3002` | `3002` |
| Health check path | `/health` | `/health` |
| Runtime command | Dockerfile `CMD` (`node dist/index.js`) | Dockerfile `CMD` (`node dist/index.js`) |

Both environments use the same container and health-check port (`3002`). Do
not configure `3005`: the proxy defaults to `PORT=3002`, exposes `3002`, and
the image health check probes `127.0.0.1:3002/health`. A port mismatch leaves
the Coolify application unhealthy even when the Node process starts.

The health endpoint returns `{"status":"ok","service":"proxy"}`.

Runtime environment variables must be configured in Coolify (not in the repo):
`NODE_ENV`, `PORT`, `CORS_ALLOWED_ORIGINS`, `SYNC_ERP_API_URL`, `SYNC_ERP_API_SECRET`,
`SYNC_ERP_BOT_URL`, `SYNC_ERP_BOT_SECRET`, `PROXY_API_SECRET`,
`SANTI_LIVING_COMPANY_ID`, `PUBLIC_BASE_URL`, `ADMIN_WHATSAPP_NUMBER`,
`MIDTRANS_IS_PRODUCTION`, `MIDTRANS_SERVER_KEY`, `MIDTRANS_CLIENT_KEY`
(see `apps/proxy/.env.example` for the full list and semantics).

## Deployment verification

1. After the workflow succeeds, open Coolify and confirm the deployment shows
   "running" (or "healthy" once the health check passes).
2. Health check from the host that can reach the app:

   ```bash
   curl --fail --silent http://<coolify-app-domain>/health
   ```

   Expected: `{"status":"ok","service":"proxy"}` and HTTP 200.
3. Smoke-test one authenticated endpoint (for example a tRPC query) before
   considering the deploy complete.

## Manual trigger from LAN (fallback without tunnel)

```bash
curl --fail --show-error --silent --max-time 30 -X POST \
  --header 'Content-Length: 0' \
  "<staging-or-production webhook URL>"
```

The API-deploy webhook URL is intentionally secret — do not commit it or print
it in shared logs.

## Rollback

- **Preferred**: redeploy the previous Git SHA — in Coolify, open the
  application → Deployments, select the last known-good deployment, and use
  its redeploy button.
- **If Coolify is unreachable**: the previous deployment keeps running; fix
  access (or start a new tunnel) before attempting further triggers.
- **If a bad commit must be reverted**: `git revert <sha>` on `dev` (staging)
  or `main` (production), push, then trigger the workflow manually. Never
  force-push to recover a deploy.
- Verify the health endpoint after every rollback, as above.
